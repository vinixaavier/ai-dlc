## Local lock/package observations

* Platform wrapper charts are all version `0.1.0`; their lock files pin the local file dependencies (`loki` 7.3.0, `tempo` 1.24.4, `grafana` 10.5.15). Their lock `generated` timestamps are 2026-09-19, while Loki's nested lock was generated 2026-06-13 and rollout's nested lock 2026-06-10. This is evidence of lock age/inconsistent regeneration, not proof of an available update.
* Checked-in Loki package `loki-7.3.0.tgz` contains the same chart metadata and nested charts (`minio`, `grafana-agent-operator`, `rollout-operator`, `crds`); Tempo package `tempo-1.24.4.tgz` contains only its root chart metadata. The package contents therefore do not establish that remote dependencies are current.
* Local Loki dependencies are MinIO 5.4.0, Agent Operator 0.5.2, and rollout-operator 0.50.0. The current community Loki chart drops Agent Operator, keeps MinIO 5.4.0, and uses rollout-operator 0.52.0. This is a structural migration, not just version drift.
* Local Tempo is a single-binary chart (`name: tempo`) while upstream references are `tempo-distributed`; chart identity/topology differs. The community chart is not a drop-in replacement without values and operational review.

## Uncertainties and verification boundaries

1. “Latest” means the release/tag/index visible on 2026-09-20. OCI registries and GitHub API can expose tags that are not represented in a legacy HTTP index; where an index and GitHub release disagree, the report records both rather than choosing by semver.
2. No deployment values were rendered or compared. Compatibility, CRD behavior, storage schema, image overrides, and upgrade safety remain unverified.
3. MinIO's chart index has no newer chart than 5.4.0, but its software repository is archived and its distribution/support model changed. A safe recommendation requires an explicit storage-owner decision, not automatic chart refresh.
4. The wrapper `Chart.lock` digests were not recomputed because this assessment intentionally made no changes; digest freshness should be checked during an approved migration PR.

## Suggested order of work (future change, not performed)

1. Decide whether Loki/Tempo/Grafana should move to `grafana-community` repositories and validate Kubernetes >=1.25.
2. Decide Alloy migration for every Agent Operator use before upgrading Loki/Tempo charts.
3. Decide MinIO versus another supported object store before changing Loki storage dependencies.
4. Render old/new charts with repository values, compare CRDs and workload topology, then regenerate and verify locks and packaged artifacts.
